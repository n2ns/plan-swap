# Manual Verification

Purpose: acceptance procedures and expected observations for the sidebar and account flows. These are checklists, not evidence that a check has passed. Product behavior belongs in [Features](features.md); pending checks remain in [TODO](../TODO.md). Build and package instructions are in [Development](development.md).

## Preview verification

Every frontend change must be checked in the preview page at sidebar/container widths **200, 240, 280, 340 and 420px**, in English, Simplified Chinese, Traditional Chinese, Spanish and Japanese, with screenshots and assertions in the report. `npm run test:ui` asserts the layout rules (no horizontal scroll, wrapping, tag group placement); review its artifacts, and check by eye anything a change adds that it does not assert.

Use a headless browser (the default of `npm run test:ui`, or a headless browser for manual preview checks); do not open a browser window on the user's display. Keep 100% zoom with a fixed viewport (a headed browser, only when explicitly requested, stays full-screen). Adjust the sidebar or preview container width, not the browser viewport or page zoom.

During preview verification, every agent (the main agent and each subagent independently) opens exactly one browser tab for the task and reuses it with `navigate_page` (reload or change URL parameters). Do not share tabs between agents or call `new_page` repeatedly. Include this rule in any delegated frontend verification task. When finished, close the tab you opened and stop the preview static server by its PID. Never kill processes by name; only clean up processes started for the current task.

For the repeatable fixture page and automated checks, see [Development: Repeatable Webview checks](development.md#repeatable-webview-checks). The runner saves screenshots and JSON assertions under `.test-out/ui/`; review those artifacts as well as the exit status.

A static preview verifies layout, not the real editor integration or account switching. Report those checks separately. The real-account steps below are performed by the user; a preview does not authorize writing account data or restarting a WSL server.

## WSL setup and safety

### Setup

`npm test` covers modules and mocked host interactions, not a real Webview; for changes affecting UI behavior, verify the affected flows manually in a **WSL window**, either with the packaged vsix (`Extensions: Install from VSIX...`) or in the Extension Development Host (F5). Both are described in [Development](development.md); if F5 never attaches, see [F5 troubleshooting](development.md#1-f5-does-not-load-the-extension-in-vs-code-1139-js-debug-attach-regression). In the development host, disable an installed vsix of this extension first (it would register duplicate commands and views), and use `Developer: Open Webview Developer Tools` for the frontend console (e.g. CSP errors).

This checklist creates and deletes directories under the real `~` and is performed by the user personally; agents must never perform its write or delete steps in the real home directory themselves. Using test accounts is recommended to avoid deleting real account directories by mistake.

### Command Palette sharing

For each provider, prepare an independent named test account that is not current (and, for Codex, not selected). Run **Share with Default Account** from that provider's Command Palette category. Check that the picker uses aliases and excludes default, external, already shared and in-use selections. Cancel the picker, then repeat and cancel the conversion modal: account files must remain unchanged. Confirm on a disposable account to exercise the same conversion and busy checks as the sidebar sharing procedures below. With no eligible accounts, expect **No accounts to choose from.** Verify the command title and picker prompt in English, Simplified Chinese, Traditional Chinese, Spanish and Japanese. Real-account conversion remains user-operated.

   **Sidebar buttons** ([Usage refresh buttons](features.md#usage-refresh-buttons)): in the real editor, both pages show the `refresh` and `layers` buttons exactly when the visibility rules there say so; judge their look in light, dark and high-contrast themes.

## Native Windows (user-operated)
